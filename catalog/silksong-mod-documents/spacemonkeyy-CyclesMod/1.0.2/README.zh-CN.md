# CyclesMod

该模组使循环与加载时间无关。这意味着，无论你的电脑性能如何强大或薄弱，你都可以制作出即使荒谬且极度精确的循环。需要注意的是，此模组允许创建一些原本无法实现的循环，可能会让你在某些循环中过快，这种情况可通过调整设置来解决。

# 如何使用

Normalize Cycles 是该模组的主要设置。关闭此设置意味着每次重新加载房间时，循环行为都会有所不同。你仅应在故意制造不良载入或尝试重现特定 PC 配置时才关闭此设置。

默认情况下，循环将在理论上理想条件下运行，如同载入是瞬时完成的一样。这意味着物体的循环会尽可能晚地开始。你可以通过修改 Extra Load Time 设置来设定一个相对于理想时间的具体偏移量。例如，将 Extra Load Time 设为 0.1s 表示循环将比理想时间提前 0.1s 开始。如果你发现开启 Normalize Loads 会导致你必须放慢速度以确保循环正常运行，你应该增大此设置值。

Force Clear Memory 仅用于研究目的。它会引入额外的变异性，很可能导致循环失去同步。这与循环提前开始是不同的：这意味着房间内的不同物体将各自在不同时刻开始运行。再次强调，这是为了实验不良载入情况而设计的。

设置速查表：

- 最佳载入：Normalize Loads = 开启，Extra Load Time = 0.0，Force Clear Memory = 关闭  
- 良好载入：Normalize Loads = 开启，Extra Load Time > 0.0，Force Clear Memory = 关闭  
- 原始载入（Vanilla）：Normalize Loads = 关闭，Extra Load Time = 0.0，Force Clear Memory = 关闭  
- 差劣载入：Normalize Loads = 关闭，Extra Load Time > 0.0，Force Clear Memory = 开启

# 加载机制说明

丝之歌（和空洞骑士）仅保留当前房间的加载，其余地图区域始终被卸载。每当玩家进行屏幕切换时，游戏会暂停以加载新房间并卸载旧房间。这个过程被称为“加载”。加载所需的时间取决于多种因素，但一般来说，性能更好的 PCs 会更快完成加载。这就是为什么空洞骑士和丝之歌速通使用自动分段器（autosplitter）在加载期间暂停计时：否则，配置较差的电脑用户将被迫以相同的游戏表现获得更慢的成绩。

人们普遍认为，较长的加载时间会导致较差的循环性能，因为游戏在加载结束、玩家重新获得控制权时已经运行了更长时间。然而，这**实际上并非 true**（至少不是严格意义上的）。为了说明原因，并展示真正导致循环差异的因素，我们需要深入分析加载过程的具体结构。

游戏内部将一次加载划分为多个不同阶段，称为“阶段”。以下是对每个阶段作用的简要总结。不总是运行的阶段已用斜体标出。

- *FetchBlocked*：在某些平台和特定切换场景中，游戏会等待摄像机变黑后再继续。此阶段通常被跳过。
- *ClearMemPreFetch*：如果游戏内存不足，系统将手动执行垃圾回收以释放空间用于加载。该阶段很少运行，耗时约 0.1 秒或更少。
- 加载（Fetch）：游戏从游戏文件中将新场景的所有资源加载到内存中。此阶段占加载时间的大部分，耗时从 0.1 秒到 2 秒甚至更长，具体取决于硬件性能和新场景中对象的复杂程度（例如，e.g. 的城镇会比大多数房间花费更多时间）。
- *ActivationBlocked*：游戏等待摄像机完成变黑（如果尚未完成），而通常此时已经完成。
- 激活（Activation）：游戏实例化场景中指定的所有对象，包括为每个对象运行 `Awake()`。此阶段耗时约 0.05 秒。
- *ClearMemPostActivation*：游戏再次检查内存是否不足，并在必要时释放部分资源。该阶段的频率与 ClearMemPreFetch 相似，耗时约为 0.3 至 0.4 秒。如果你启用了模组设置中的“强制清空内存”选项，此阶段将始终运行。
- GarbageCollect：此阶段总是运行（除非已执行 ClearMemPostActivation），并进行一次更快的垃圾回收。耗时不超过 0.1 秒。
- StartCall：游戏等待恰好一帧（或是否如此？）。这使得新实例化的对象能够运行其 `Start()` 方法，大型场景中该方法可能耗时高达 0.1 秒。
- *LoadBoss*：某些场景包含一个额外的“首领场景”，只有在首领仍存活时才需要单独加载。此场景通常比主场景小得多，因此该阶段耗时约为 0.5 至 1 秒。

尽管每个阶段都会受到电脑性能一定程度的影响，但加载时间的主要差异来自“加载”阶段。该阶段的长度主要由计算机硬盘的速度决定。然而，此阶段与循环性能无关。新场景中的对象只有在激活阶段之后才真正存在，因此在此之前任何阶段都无法影响它们的行为。

真正的元凶出人意料地是 StartCall。但为什么这样合理呢？你可能会认为，StartCall 的差异最多只会使循环时间偏移一帧，即在 60fps 下为 0.016 秒，更高帧率下则更短。尽管如此，这一帧是由于游戏在此帧上执行大量工作而产生的延迟帧，但即便如此，误差也应最多为 0.1 秒。事实上，你判断得没错。问题不在于 StartCall 做了什么，而在于它**没有做**——因为它在之前的阶段中被错误地执行了。

# The Problem

由于游戏开发者的一个疏忽，很可能在 `Start()` 方法执行之前，StartCall 尚未开始。这是因为 `Start()` 在对象首次存在时的首帧被调用，而该帧始终出现在激活阶段之后的第一帧。这一帧会发生在 ClearMemPostActivation 或 GarbageCollect 阶段之中，这两个阶段都会进行较为粗暴的内存清理操作。这导致了帧内出现多个微小的卡顿峰值，再加上由 `Start()` 方法本身引起的卡顿峰值（其中部分方法运行速度较慢），整体表现尤为不佳。

即便如此，这一切都不应该有影响，因为所有内容仍然在同一个帧上开始。由于时间仅在帧之间以离散步骤前进，所有内容应该仍在相同的游戏时间点启动并正常运行。但显然情况并非如此。出于某种神秘的原因，Unity将会强制中断一帧以启动新帧，如果第一帧存在足够延迟，可能为了“追上”帧率。而在这两帧之间，游戏时间不同，因为整个加载过程中的时间均以正常速度运行（除了激活阶段，我认为）。由于这两帧都是延迟帧，这种时间差可能会非常显著；这种情况尤其在true如果ClearMemPostActivation正在运行。我怀疑时间可能偏差达00.5秒，足以在冲刺状态下水平移动数倍于玩家宽度的距离。显而易见，这是一个巨大的差异。

还存在一个严重问题，使整个混乱局面雪上加霜。StartCall阶段会等待一帧，在此期间允许剩余的`Start()`方法执行。但在极差的情况下，并不会发生这种情况。实际上，只有*大部分*的`Start()`方法会在该帧中运行。我认为这与Unity在每一帧中访问对象的顺序有关。负责加载代码的对象位于这一顺序的中间位置，因此当它在等待一帧后被唤醒时，只有部分对象已经完成更新。当然，这种情况本不应产生影响，因为这些对象本应在前一帧中就已经更新完毕，但Unity却表现异常。由于StartCall通常是最后执行的阶段，游戏仅以部分对象已启动的方式“完成”加载过程。这进而引发了一系列新的事件，使游戏运行更加卡顿。如果StartCall等待两帧而非一帧，则此问题将消失。

这些问题解释了为什么房间内的某些物体可能会从不同时间开始它们的循环。更严重的问题是，循环的起始时间会因加载过程而提前或延后，原因在于在此期间时间仍然正常流逝。因此，根据你在这几帧中所遇到的延迟程度，你可能在与循环同步的时间进入房间，也可能走进房间却发现循环已经先行启动了。整个加载过程的总时长对这一短暂阶段影响甚微，但 true 在性能较弱的 PCs 上可能会花费更长时间，从而导致循环表现更差。

# 该模组如何修复问题

修复方法很简单，就是在加载时暂停游戏时间，并将 StartCall 的等待帧数从一帧增加到两帧。当然，由于上述所有操作都发生在同一个方法中（感谢 Team Cherry），而这个方法恰好是一个迭代块，因此我们必须做一些非常奇怪的操作来按我们想要的方式修改它。除非你非常勇敢，否则不建议阅读该模组的代码 ;)
